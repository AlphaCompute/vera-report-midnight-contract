# Evidence V2 integration and deployment

This source change does not update an existing deployment or the VERA application. Do not point old clients at a V2 address.

1. Compile the reviewed commit with the pinned toolchain and run all tests. Run `node scripts/artifact-manifest.mjs > artifact-manifest.json` to rebuild full proving keys and capture source, dependency lock and artifact SHA-256 values. The manifest records local build provenance; it does not attest a deployment.
2. Generate a fresh deployment domain with `createDeploymentDomain()`. Deploy on the intended network with this constructor argument. Record the network identifier, domain, actual contract address, actual finalized deployment transaction, maintenance/upgrade authority and artifact manifest in the operator's deployment record. Verify the transaction link actually names the recorded transaction. Compare the deployed verifier keys with the build's keys using the network SDK before accepting submissions.
3. Add explicit `vera:evidence:v2` handling to the application. Generate a fresh 32-byte `createOpening()` for each intake attempt, durably store it with the evidence hash and idempotency key in protected storage before proving, and bind the attempt to network, address and domain. Do not derive this value from identity, tracking ID, document hash or old nullifier. An encrypted backup and documented recovery policy are required for continued private verification. Losing the opening loses this verification capability.
4. Submit only through `submitEvidenceV2`. Store the resulting public commitment/tag alongside the exact transaction identifiers and finalized receipt. A computed commitment is not evidence of acceptance: verify full transaction success at the configured address and reconcile unknown outcomes before retrying. A retry must retain its opening. Never rotate the secret simply to bypass a replay rejection.
5. Pass the retained evidence hash and opening to `verifySubmissionV2` through a trusted prover. The circuit checks their commitment's actual ledger membership; callers must bind any returned proof/receipt to the intended network, contract, circuit and commitment. The `1` return value by itself is not a portable signed receipt. Never return circuit inputs/proof-data objects in a public API.
6. Retain separate legacy receipt handling. Do not reinterpret historical accumulator roots or old nullifiers as V2 membership or randomness. A deliberate resubmission to V2 is a new event, not proof of original time or ownership.
7. On a non-production network, test finalized submission, verification after intervening submissions, duplicate rejection, process restart/receipt recovery and proof-server confidentiality. Validate production toolchain/network compatibility and deployed bytecode identity before activation.

No process here can independently establish CSPRNG quality, prover confidentiality, reporter identity or deployed source correspondence from local runtime tests alone. The public deployment domain must be different for each network/address; the contract enforces nonzero, while the deployment process must enforce uniqueness.
